# CUDA 13.5 adoption — implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Remove the mixed-toolkit build state, make the next toolkit swap fail
loudly, and adopt CUDA 13.5's family-specific arch targets with the hardware NVFP4
decode — kept only where measured.

**Architecture:** Task 1–2 are build-system hygiene (configure-time stamp +
a test that reads it). Task 3 is the arch mechanism (`LSX_CUDA_ARCH` as
`120f;121f`, expanded to explicit `--generate-code` because CMake 4.2.3 drops the
`f` suffix). Task 4 adds the family-specific FP4 decode behind a bit-exact gate.
Task 5 measures and re-seeds or reverts. Task 6 updates the docs/skills.

**Tech Stack:** CMake 4.2.3, CUDA 13.5.37 (driver 13.2), Catch2 guards,
`cuobjdump`/`nvcc -ptx` for evidence, `test_perf_baseline` for throughput.

**Spec:** `docs/superpowers/specs/2026-11-05-cuda-13.5-adoption-design.md`

## Global Constraints

- Blackwell consumer only: CC 12.0/12.1; never add 100/103/110/112 targets.
- One source of truth for device codegen: `LSX_CUDA_ARCH` (guard rule 3 forbids
  arch literals elsewhere).
- A gate result is never rewritten; a SKIP/`not run` stays a gap.
- Perf rows are written by the harness only; never hand-edited.
- Bit-exactness before throughput: no number is quoted from a non-bit-exact run.
- GPU exclusivity: one model process at a time.

## Review Focus

- **A configure that succeeds while the objects are stale.** That is the defect
  being fixed; a stamp that is written but never compared changes nothing.
- **`sm_120f` silently becoming `sm_75`.** CMake's fallback is quiet and the
  binary still runs (PTX JIT), so only a guard or an `arch = ` inspection sees it.
- **A family-specific decode that is one E2M1 level off.** Values are exact in
  BF16, so any difference is a bug, never rounding — compare all 16 nibbles and
  the real-weight `logits_hash`.
- **A throughput claim from a hot or shared GPU.** The environment oracle must be
  clean and the card idle; otherwise the row is ENVIRONMENT, not a delta.
- **Host-only code pulling device intrinsics.** `cuda_fp4`/`cvt` must stay inside
  the device-only branch or host builds (and `test_core`) stop compiling.

### Task 1: Toolkit build stamp (configure-time guard)

**Files:**
- Modify: `CMakeLists.txt` (next to the existing toolkit-consistency guard)
- Test: `tests/test_infrastructure_guard.cpp` (new rule case)

**Interfaces:**
- Produces: `${CMAKE_BINARY_DIR}/lsx_cuda_toolkit_stamp.txt`, one line,
  `toolkit=<CUDAToolkit_VERSION> cccl=<value> nvcc=<CMAKE_CUDA_COMPILER_VERSION>`;
  a `FATAL_ERROR` naming the file and the wipe command when it changes.

- [ ] **Step 1: Write the failing test** — in `test_infrastructure_guard.cpp`, a
  case `TEST_CASE("Rule 8: configure cannot reuse a build tree from another toolkit")`
  that reads the root `CMakeLists.txt` and requires both markers
  `lsx_cuda_toolkit_stamp.txt` and a `FATAL_ERROR` mentioning
  `cmake --preset` / wipe, plus that `${CMAKE_BINARY_DIR}` is not written from a
  subdirectory (it appears exactly once).
- [ ] **Step 2: Run to verify it fails** — `test_infrastructure_guard` fails on
  the missing markers.
- [ ] **Step 3: Implement** — after the existing toolkit-consistency block:
  build `_lsx_stamp` string from the three versions; if the stamp file exists and
  differs, `message(FATAL_ERROR "build/ was configured for <old> but the toolkit is
  <new>; wipe the build directory (rm -rf build/<preset>) — CMake cannot see the
  toolkit headers change because they carry package mtimes")`; else write it with
  `file(WRITE)`.
- [ ] **Step 4: Run to verify** — guard test green; `cmake --preset linux-debug`
  writes the stamp; deleting the file and re-configuring writes it again.
- [ ] **Step 5: Commit** — `build: stamp the toolkit a build tree was configured with`.

### Task 2: The stale-tree test (what configure cannot see)

- Produces: a case that fails when the stamp's `toolkit=` disagrees with the

- [ ] **Step 1: Write the failing test** —

- [ ] **Step 2: Run to verify it fails** — before Task 1's file exists the case
  fails with "no stamp".
- [ ] **Step 3: Implement** — the case above; add the compile definition in
  `tests/CMakeLists.txt` next to the existing `test_cuda_toolkit_guard` target.
- [ ] **Step 4: Run to verify** — green on a clean tree; then simulate staleness
  by editing the stamp to `13.4.x` and confirm the test fails, then restore.
- [ ] **Step 5: Commit** — `test(cuda): a stale build tree fails the toolkit guard`.

### Task 4: Family-specific arch targets

**Files:**
- Modify: `CMakeLists.txt` (`LSX_CUDA_ARCH` value + a `lsx_cuda_gencode_flags()` helper or an equivalent expanded cache entry), `cmake/LsxTestHelpers.cmake`, `tests/CMakeLists.txt`, `libs/*/CMakeLists.txt`, `apps/*/CMakeLists.txt` (the `CUDA_ARCHITECTURES "${LSX_CUDA_ARCH}"` sites)
- Test: `tests/test_infrastructure_guard.cpp` (extend rule 3), `tests/test_cuda_toolkit_guard.cu`

**Interfaces:**
- Produces: `LSX_CUDA_ARCH` default `120f;121f`; every device target sets
  `CUDA_ARCHITECTURES OFF` and compiles with
  `--generate-code=arch=compute_<N>f,code=[compute_<N>f,sm_<N>f]` per entry.
- Produces: a guard case that fails when any device target passes a bare `f`
  spec to `CUDA_ARCHITECTURES` (CMake would silently emit `compute_75`).

- [ ] **Step 1: Write the failing test** — extend rule 3 in
  `test_infrastructure_guard.cpp`: a case asserting (a) no `CUDA_ARCHITECTURES`
  argument contains an `f` suffix, (b) the root CMakeLists defines both
  `LSX_CUDA_ARCH` and the gencode expansion marker, (c) a synthetic source string
  `set_target_properties(x PROPERTIES CUDA_ARCHITECTURES "120f")` is flagged.
- [ ] **Step 2: Run to verify it fails** — the current `LSX_CUDA_ARCH` is
  `120-real;121-real` and no gencode marker exists.
- [ ] **Step 3: Implement** — in the root: default `LSX_CUDA_ARCH "120f;121f"`,
  and build `LSX_CUDA_GENCODE_FLAGS` from it (split on `;`, strip a trailing `f`,
  emit the two `--generate-code` pairs) with a `FATAL_ERROR` on a non-12x or
  non-`f` entry; replace every `CUDA_ARCHITECTURES "${LSX_CUDA_ARCH}"` with
  `OFF` + `$<$<COMPILE_LANGUAGE:CUDA>:${LSX_CUDA_GENCODE_FLAGS}>`.
- [ ] **Step 4: Run to verify it passes** — guard green; a rebuilt target shows
  `arch = sm_120f` in `cuobjdump`, and no `compute_75` anywhere in `flags.make`.
- [ ] **Step 5: Verify the whole tree** — full rebuild, `ctest --preset
  linux-debug` 134/134, one real-weight SelfCheck bit-exact (qwen3.5-9b or the
  family chosen in Task 5).
- [ ] **Step 6: Commit** — `build: family-specific sm_120f/sm_121f device codegen`.

### Task 5: Hardware E2M1→BF16 decode, measured

**Files:**
- Modify: `libs/lsxcommon/src/nvfp4_codec.h`
- Test: `tests/test_lsx_kernels.cu` (family-specific bit-exact case)

**Interfaces:**
- Consumes: `E2M1Value(int nib) -> float` (unchanged signature on both paths).
- Produces: the device path uses `cvt.rn.bf16x2.e2m1x2` under
  `#if defined(__CUDA_ARCH_FAMILY_SPECIFIC__) && __CUDA_ARCH_FAMILY_SPECIFIC__ >= 1200`,
  and is `memcmp`-identical to the table over all 16 nibbles.

- [ ] **Step 1: Write the failing test** —
  `TEST_CASE("E2M1Value: the family-specific decode is bit-identical to the table")`:
  a kernel that computes both paths for all 16 nibbles into two buffers and
  asserts `memcmp == 0` plus the exact expected sequence
  `{0,0.5,1,1.5,2,3,4,6,-0,-0.5,-1,-1.5,-2,-3,-4,-6}`.
- [ ] **Step 2: Run to verify it fails** — the family-specific branch does not
  exist, so the test cannot compile/link its second path (expected: missing
  symbol / identical-to-table assertion not reached).
- [ ] **Step 3: Implement** — add the branch; keep the table as the host path and
  the reference; document that the instruction is `F2FP.BF16.E2M1` in SASS.
- [ ] **Step 4: Run to verify** — the new case green, the pre-existing exhaustive
  table case still green, `test_lsx_kernels` fully green.
- [ ] **Step 5: Verify numerically on real weights** — SelfCheck of the measured
  family: `logits_hash` must equal the Task 3 value exactly.
- [ ] **Step 6: Commit** — `perf(nvfp4): family-specific E2M1 decode behind a bit-exact gate`.
