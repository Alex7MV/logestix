# CUDA 13.5 adoption — design (2026-11-05)

## Intent

The host moved from CUDA Toolkit 13.4.92 to **13.5.37** while the driver stayed at
`595.99.02` (= CUDA 13.2). Two pieces of work follow from that, and one is not an
optimisation but cleanup: an existing build tree was left half-rebuilt, because
CUDA's own headers are dated (13 Oct) *older* than objects built in late October,
so no build system rule considers them changed. The second is the only thing in
13.5 that can touch our numbers on this hardware: **family-specific arch
targets** (`sm_120f`/`sm_121f`), whose SASS replaces the emulated NVFP4→FP32
decode with a single `F2FP.BF16.E2M1` instruction.

Out of scope by operator decision: everything that needs a newer **driver**
(oversized shared memory, locality domains, TMA large-allocation class,
memcpy-batch graph nodes, fabric/cliques). Verified unavailable here: the
attributes return `CUDA_ERROR_INVALID_VALUE` and the entry points are absent from
`libcuda.so.595.99.02`.

## Why now / what "done" means

- A build tree must never mix objects compiled against two toolkits, and today
  nothing fails when it does. Done = configure refuses, and a test catches what
  configure cannot (a test binary run in a stale tree).
- Family-specific codegen is only worth shipping if it is measured. Done = an A/B
  on a compute-bound family at the canonical 2048-token protocol, bit-exact
  throughout, with the row re-seeded only on a win; a loss is recorded and
  reverted.

## Goals

1. A clean 13.5 tree, and a mechanism that makes the *next* toolkit swap loud.
2. `sm_120f`/`sm_121f` device codegen through one source of truth
   (`LSX_CUDA_ARCH`), with the CMake `f`-suffix trap closed.
3. Hardware E2M1→BF16 conversion in the NVFP4 codec, **behind a measured
   decision**, bit-identical to the existing table.
4. Docs/skills updated so the next session reads 13.5 as the validated toolkit.

## Non-goals / anti-goals

- Non-goals: driver-gated 13.5 features; PTX `.target sm_120f` for any arch we do
  not run (110/103/100); `--concat`, `--fdevice-time-trace`, `-Wconversion` —
  build-time conveniences with no output effect (recorded, not adopted).
- Anti-goals: shipping family-specific arch **unmeasured**; leaving the build
  tree in a mixed state "because it still links"; adopting a 13.5 header codec
  path whose values differ from the table — a routing-scale decode that is one
  E2M1 level off is a correctness defect, not rounding.

## Constraints (verified, not assumed)

| fact | evidence |
|---|---|
| toolkit 13.5.37, PTX ISA 9.5 | `nvcc --version`, `.version` in `-ptx` output |
| driver 13.2 (`595.99.02`) | `nvidia-smi`, `cuDriverGetVersion` |
| CCCL 3.5.0 (`3005000`), inside band `[3002000, 3006000)` | configure log |
| `sm_120f` cubins **run** on this sm_120 card | probe kernel: `kernel status: no error` |
| `sm_120` codegen emulates FP4 decode; `sm_120f` uses `F2FP.BF16.E2M1.UNPACK_B` | `cuobjdump -sass` on the same source |
| **CMake 4.2.3 silently ignores the `f` suffix** and falls back to `compute_75`, even for `120-real;121f-real` | `flags.make` shows `--generate-code=arch=compute_75` |
| `CUDA_ARCHITECTURES OFF` + explicit `--generate-code=arch=compute_120f,...` produces real `sm_120f` | `cuobjdump` shows `arch = sm_120f` |
| 1250 of 1460 objects predate the upgrade | `find -newermt` |

## Approaches

**A. Stamp + fail (chosen).** At configure time write the toolkit and CCCL
version into `${CMAKE_BINARY_DIR}/lsx_cuda_toolkit_stamp.txt`; on the next
configure, if it differs, `FATAL_ERROR` with the wipe instruction. A Catch2 case
in `test_cuda_toolkit_guard` reads the same stamp and compares it with
`CUDART_VERSION`, so a stale tree fails *at test time* too. Trades a manual wipe
after a toolkit swap (40 min) for the guarantee that no mixed build is ever
silent.

*Rejected:* auto-wiping the build directory inside configure — it destroys a
possibly-hot cache for a change the human may be about to revert, and CMake has
no way to make that reversible. *Rejected:* relying on `test_cuda_toolkit_guard`
alone (it works — it caught this — but only after a full build, and only if
someone runs it).

**B. Family arch through `LSX_CUDA_ARCH` + generated `--generate-code` (chosen).**
Keep one cache variable as the single source of truth, but express it as
`120f;121f` and expand it in the helpers into explicit
`--generate-code=arch=compute_Nf,code=[compute_Nf,sm_Nf]` flags with
`CUDA_ARCHITECTURES OFF`. Trades a full rebuild and a slightly more manual arch
input for real family-specific codegen; the alternative (leave `120-real`) keeps
the emulated FP4 path forever.

*Rejected:* passing `120f-real` to CMake as-is — it silently produces `sm_75`
code, which would still run (PTX JIT) and be slower than today, the worst
outcome. *Rejected:* adding `--generate-code` on top of `120-real;121-real` —
duplicate cubins in every fatbin.

**C. Hardware FP4 decode behind a compile-time family check (chosen, measured).**
In `nvfp4_codec.h`, when `__CUDA_ARCH_FAMILY_SPECIFIC__ >= 1200`, decode a
nibble with `cvt.rn.bf16x2.e2m1x2` and widen to float; otherwise keep the
`0xC8643210` table. Both paths must be **bit-identical** — E2M1 values are exact
in BF16 — and the gate is an exhaustive 16-value device comparison plus the
existing full-vocabulary `logits_hash` on real weights.

*Rejected:* replacing the table outright (the table is also the host reference
for every kernel test, and `kOff`/debug builds must not depend on a
family-specific instruction). *Rejected:* adopting the 13.5 `__nv_cvt_fp4_*`
headers wholesale — they pull `cuda_fp4.hpp` into the hot GEMV path, and the
instruction is available directly.

## Decisions (mine, per operator's "do as proposed")

1. Ship A unconditionally; ship B only if measured neutral-or-better; ship C only
   if measured faster, else record the negative and keep the table.
2. A/B reference family: **qwen3.5-9b** (160.92 t/s `perf` row, dense, compute-
   bound, short load) with `test_perf_baseline`; the environment oracle must be
   clean for a delta to count.
3. Bit-exactness gate before any number: `logits_hash` unchanged on a real-weight
   SelfCheck of the family being measured.
4. The `f`-suffix trap gets a machine check (guard test rule), not just a comment.

## What is left to the builder

Exact stamp file name/format, the wording of the configure error, how the
helpers format the gencode flags, and which guard rule hosts the `f`-suffix case
— the plan fixes these.
