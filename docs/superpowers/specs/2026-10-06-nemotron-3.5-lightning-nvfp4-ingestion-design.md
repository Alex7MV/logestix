## Stage 0 — triage

### 0.1 Classification: **sibling variant, not a new family**

The NemotronH family is already ingested from the **BF16** distribution
(`nemotron-3.5-lightning-30b-a3b`, `nemotron_moe_constants.h`). The vault now
holds only the **pre-quantized** distribution
`NVIDIA-Nemotron-3.5-Lightning-30B-A3B-NVFP4`.

`config.json` `model_type = nemotron_h`, `architectures = [NemotronHForCausalLM]`
— identical architecture, identical layer mix. Per Stage 0.1 this is a **sibling
variant**: the parent's constants header, loader, kernels, expert cache and
model class are reused. Only the **converter** needs a new source-layout path
(the source tensors are already quantized, not BF16).

The registry rows that must be extended (same commit):

| registry | row |
|---|---|
| `test_code_naming_guard.cpp` | `SchemeRegex()` variant token `nvfp4` |
| `test_model_independence_guard.cpp` | `kPassports` (new kType → parent passport header + parent ns is **not** allowed: ns must be unique) |
| `test_model_suite_guard.cpp` | `Suites()` row + tool-verdict row |
| `test_model_independence_guard.cpp` | `kLifecycle` row |

> **Correction to the "reuse the parent's passport header" shortcut.** The
> independence guard requires every `kPassports` row to own a *unique*
> namespace (`TEST_CASE("model constants namespaces are unique per model")`),
> and `TEST_CASE("each passport defines its geometry in its own namespace or
> class")` maps header → expected declaration. A sibling variant therefore
> needs its **own** constants header with the same frozen values. The Stage 0.1
> shortcut ("reuse the parent's constants header") is only sound when the
> variant is not itself a registered model. Here the pre-quantized distribution
> is a separately registered model, so it gets its own passport header that
> re-declares the identical geometry (frozen geometry is per *model*, and both
> models are the same model numerically — the difference is only the source
> encoding).

### 0.6 Semantics to verify before trusting any output

This is the crux of this variant. The source is **already quantized by ModelOpt
0.44.0rc5**, and its encoding differs from the repo's in three ways:

1. **Routed + shared experts and `lm_head`: `W4A16_NVFP4`.**
   `U8` packed E2M1 nibbles + `F8_E4M3` block scale per 16 (shape `[R, C/16]`)
   + `F32` per-tensor `weight_scale_2`.
   The repo's decoder (`nvfp4_codec.h::E4M3ScaleToFloat`, `nvfp4_scale.h`) is
   **power-of-two-only**: it reads the e4 exponent field and *ignores the 3
   mantissa bits*. Measured on the real tensor
   `backbone.layers.1.mixer.experts.0.down_proj`:
   - source block-scale mantissa bits use **all 8 values {0..7}**;
   - a naive byte passthrough therefore decodes with a **median 0.73× / max 1.00×
     per-block scale error → 29.9 % relative L2 error** on the expert weights.
   → **a raw fp4 passthrough is forbidden.** The converter must *dequantize*
     (full E4M3) and *requantize* through the repo's own `quantize_tensor_gpu`,
     exactly like the MiMo MXFP4 `FallbackProjection` path. Measured cost of that
     dequant→pow2-requantize round trip vs the source NVFP4 dequant:
     **10.9 % / 11.2 % / 11.8 % relative L2** on three expert tensors. That is the
     price of the repo's documented pow2-only deviation, and it is the same
     deviation every other ingested family already carries.

2. **Mamba `in_proj` / `out_proj`: `FP8` (per-tensor).**
   `F8_E4M3` weights + a **scalar** `F32 weight_scale` (shape `[]`) + `F32
   input_scale`. Not block-128. Dequantize as `value * weight_scale`, then
   requantize to NVFP4 through `quantize_tensor_gpu`.
   (`ws * 448 = 0.504` for `in_proj` — consistent with an E4M3 per-tensor amax
   of ~0.5.)

3. **Attention `q/k/v/o_proj`: `BF16` (unquantized), `k_proj.k_scale` /
   `v_proj.v_scale` present as `F32[1]`.**
   These are the **FP8 KV-cache** scales from `hf_quant_config.json`
   (`kv_cache_quant_algo: FP8`), **not** weight scales: the weights are BF16.
   The repo runs an FP16 KV cache, so these scales must be **classified and
   dropped** (they are not weight dequant factors — applying them would corrupt
   attention). The parent's converter classifies `q/k/v/o_proj` as NVFP4 and
   quantizes them from BF16; that stays correct here since the source is BF16.

Other semantics carried over unchanged from the parent (verified against
`config.json`): full-dim RoPE (`partial_rotary_factor = 1.0`, no scaling),
`norm_topk_prob = true`, `routed_scaling_factor = 2.5` applied by the router,
`sliding_window = null`, `time_step_*` clamping handled by the parent's kernels,
`moe_shared_expert_overlap = true` (shared expert is ungated, added to the routed
accumulation).

## Stage 1 — topology and structure passport (lsxforge)

New converter TU `libs/lsxcommon/src/nemotron_moe_nvfp4_convert.{h,cpp}`,
pipeline flag `--nemotron-nvfp4` (`apps/lsxforge`), writing the **same**
`logestix-nemotron-nvfp4` layout the parent's loader reads — so the parent's
loader, expert cache, kernels, model class and tool format are reused verbatim.

Two responsibilities the parent's converter does not have:

- **Scale-tensor classification.** `classify_nemotron_tensor` must recognize
  and route the source's companion scale tensors instead of rejecting them:
  `*.weight_scale`, `*.weight_scale_2`, `*.input_scale`, `*.k_scale`,
  `*.v_scale`. A scale tensor whose base weight is missing is an error.
- **Source-layout dispatch per tensor**, chosen from the *observed dtype*
  (never from a filename guess):
  | observed | handling |
  |---|---|
  | `U8` + `F8_E4M3 weight_scale[R,C/16]` + `F32 weight_scale_2` | NVFP4 → dequant → `quantize_tensor_gpu` |
  | `F8_E4M3` + scalar `F32 weight_scale` | FP8 → dequant → `quantize_tensor_gpu` |
  | `BF16` | existing path (`quantize_tensor_gpu` or raw) |
  | `F32` | raw |

The two eos ids (`[2, 11]`) and the `experts_no_gate` / `mtp_tensors` accounting
are written into `model.index.json`; the loader's index parser gains the eos
**list** (`eos_token_id` may be an int or an array).

## Stage 2 — quantization

`quantize_tensor_gpu` is the single neutral quantization entry point; the
converter only *feeds* it dequantized BF16. New GPU dequant kernels
(`nemotron_moe_nvfp4_dequant.cu`, role `dequant` is in the naming scheme):

- `NemotronNvfp4ToBf16` — `U8` nibbles + **full E4M3** block scale + `F32`
  global scale → BF16 (uses `__nv_cvt_fp8_to_halfraw`, the *complete* E4M3
  decode, **not** `E4M3ScaleToFloat`).
- `NemotronFp8ToBf16` — `F8_E4M3` + scalar `F32` scale → BF16.

Both are streaming (grid-stride, one element per thread) and write into a
reused device buffer, so peak VRAM stays at one tensor, not one expert set.

Norms, biases, the router and `conv1d` are never quantized (they are BF16/F32 in
the source and stay raw in the converted layout).

## Stage 3 — registration

`NemotronNvfp4Model` (`kType = "nemotron-3.5-lightning-30b-a3b-nvfp4"`),
registered in `model_registry.cpp`. The frozen-geometry cross-check in `Load`
uses the variant's own passport header and rejects a mismatch (relaxed only
under `SyntheticGeometryAllowed()`).

## Stage 4 — tokenizer bridge

Unchanged mechanism (`BuildTokenizerArrowFiles`, byte-level BPE). The variant's
index records `bos=1`, `eos=[2,11]`, `pad=0`.

## Stage 4b — tool-calling bridge

`chat_template.jinja` is present and uses the Qwen-style XML tool format:
`<tool_call><function=NAME><parameter=K>…</parameter></function></tool_call>`,
with `[AVAILABLE_TOOLS]` / `[TOOL_RESULTS]` blocks and `<think>` reasoning.
Ids 12–17 are `special: false` (they survive decode as text); ids 3–11 are
`special: true` control ids.

The parent already implements exactly this
(`RenderNemotronConversation` + `ParseQwenTokenCalls`, verified on real weights
in `2c3f301`). The variant **reuses the parent's render/parse verbatim** — same
template, same markers, same ids. Verdict: named in the tool-verdict table
alongside the parent.

## Stages 5–7 — kernels, sandbox, passport

No new kernels. The variant runs the parent's `nemotron_moe_kernels.cu`,
`nemotron_moe_inference{,_pipeline,_attn}.cu` and the neutral
`lsx_inference_nvfp4` layer. Stage 7 (thread-isolated `LsxTokenTranslator`) is
model-neutral infrastructure, already built for the parent.
