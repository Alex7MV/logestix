# Granite-4.2-30B ingestion design

## Context

`granite-4.2-30b` (IBM, `/mnt/llm_models/models/granite-4.2-30b`) is a dense
decoder-only transformer (`GraniteForCausalLM`) with a standard Llama-style
block: RMSNorm, GQA attention with full RoPE, SwiGLU MLP. It has no MoE, no
QK-norm, no linear attention, no biases. It does carry Granite's fixed
`attention_multiplier` (the attention score scale) plus
`embedding_multiplier` / `residual_multiplier` / `logits_scaling` (all 1.0
here).

Frozen geometry (from `config.json`):

| field | value |
|---|---|
| hidden_size | 4096 |
| num_hidden_layers | 64 |
| num_attention_heads | 32 |
| num_key_value_heads | 8 |
| head_dim | 128 |
| intermediate_size | 32768 |
| vocab_size | 100352 |
| rms_norm_eps | 1e-5 |
| rope_theta | 50000000 |
| attention_multiplier | 0.0078125 |
| embedding_multiplier / residual_multiplier / logits_scaling | 1.0 |
| tie_word_embeddings | false |
| hidden_act | silu |
| bos_token_id / eos_token_id / pad_token_id | 100283 / 100257 / 100257 |

This is the FIRST `granite` family member. No backward compatibility is
required (Blackwell-only repo).

## Target layout (Model Ingestion Protocol, 8 stages)

Family `granite`, type `dense`. Format tag `logestix-granite`. Model name in
`model.index.json`: `Granite-4.2-30B` (factory autodetect normalizes it to
`granite-4.2-30b`, the `kType`).

Files:

## Stage details

1. **Converter** (`granite_dense_convert.cpp`). Parse `config.json`
   (`model_type == granite`, geometry from the flat root — Granite does not
   nest under `text_config`). Classify tensors:
   `model.embed_tokens.weight`, `lm_head.weight`, `model.norm.weight`,
   `model.layers.N.{input_layernorm,post_attention_layernorm}.weight`,
   `self_attn.{q,k,v,o}_proj.weight`, `mlp.{gate,up,down}_proj.weight`.
   No unknown-layer ballast to strip. Integrity: `VerifyAllTensorReads`,
   `CheckTensorCoverage`, `CheckLayerContiguity`, `CheckGeometryFields`
   (config vs tensor shapes), `BuildAndVerifyTokenizer` (bos+eos required),
   `VerifyConvertedModel`. Emits `logestix-granite`.
2. **NVFP4** every dense linear + embed/lm_head via `gpu::quantize_tensor_gpu`
   (E2M1 + per-16 E4M3 scales + global float scale). Norms stay FP16.
   gate+up are fused into one `[2I, K]` NVFP4 record with a single global
   scale (fast MLP, same as qwen).
3. **Registration + model** (`granite_dense_model.{h,cpp}`). `Granite42_30BModel
   final : ModelBase`, `kType = "granite-4.2-30b"`, frozen `static_assert`s,
   `ValidateGeometry` vs `granite::GraniteTopology`. Registered in
   `model_registry.cpp`. `Infer` opens `LsxFastMathScope(EffectiveFastMathMode(cfg_))`.
4. **Tokenizer bridge**: reuse `BuildTokenizerArrowFiles`; Granite is byte-level
   GPT-2 BPE (`tokenizer.json` + `vocab.json` + `merges.txt`), `bos_id=100283`,
   `eos_id=100257`, `pad_id=100257`.
5. **CUDA kernels** (`granite_dense_inference.cu`): dense loop using the
   model-neutral `lsx_nvfp4` GEMM/GEMV for all projections and the shared
   `lsx_kernels_{norm,act,math}.cuh` primitives; a Granite RoPE kernel (full
   `head_dim`, θ=5e7), a causal GQA attention kernel scaled by
   `attention_multiplier`, SwiGLU MLP. One stream, no per-token sync.
6. **Shared-memory sandbox**: block-wide reductions via shared memory with
   `__syncthreads()`; no `atomicAdd` feeding `final_logits`.
7. **Passport** (`granite_dense_constants.h`, namespace `lsxcommon::granite::frozen`):
   frozen geometry is the single source of truth; no cross-includes.
8. **SelfCheck + tests + perf**: `SelfCheck` uses `runtime::RunParisSelfCheck`;
   `test_granite_dense_selfcheck.cpp` runs >=3 cycles, bit-exact determinism,
   `SKIP_RETURN_CODE 4`; `perf_baselines.json` entry + `test_perf_baseline_granite`
   target. All four guard registries extended in the same commits.

## Testing

TDD per stage. Stage 1's test builds a synthetic tiny Granite checkpoint
(2 layers, hidden 64) with `test_synth_checkpoint.h` primitives and runs the
full converter, then asserts the index metadata, the pinned arrow files and
the VRAM block. Synthetic geometry is relaxed with
`LSX_TEST_ALLOW_SYNTHETIC_GEOMETRY=1` where the model class is exercised.

## Out of scope

Multi-token KV-cache incremental decode optimization, Tensor-Core W4A4
attention fusion, and chat-template exactness beyond the byte-level BPE
bridge.

## Perf findings — lever #1 (seq==1 NVFP4 GEMV occupancy floor)

nsys attribution of a 64-token decode (Release, RTX 5090): the decode is 98%
kernel-bound; the seq==1 NVFP4 GEMV is 86% of kernel time (RmsNorm 6.2%,
attention 1.9% at short context, prefill TcGemm excluded).

Isolated decode-shape budget (`test_granite_dense_kernels`, 128 MiB L2 flush):

| shape | warp-per-row | occupancy floor |
|---|---|---|
| q/o (4096x4096) | 453 GB/s | **514** |
| gate_up (4096x65536) | 878 | 880 |
| down (32768x4096) | 587 | **824** |
| head (4096x100352) | 911 | 911 |
| aggregate | 812 | **873** |

**Root cause**: `lsx_nvfp4_gemv_warprow_kernel` launches exactly one warp per
output row, so it fills the SM array (170 SMs x 48 resident warps = ~8160)
only when `N >= ~8192`. At `N = 4096` it ran at 24 warps/SM; the K-split
sliced path (KP=4/8, 1-2 rows/block) reaches full occupancy and +35% (down)
/ +13% (q/o). **Fix**: raise the warp-per-row `N` floor from 2048 to 8192 in
`LaunchLsxNvfp4GemmSeq1GemmV` (K >= 4096 unchanged). E2E perf baseline
23.13 -> 25.33 t/s (+9.5%), reproduced at 25.36 t/s; r3 (kOff scalar tile
path) unchanged at 17.76 t/s. Selfcheck Paris x3 bit-exact still passes
(logits hash shifted under the tolerance-class GEMV route, as expected).

**Rejected**: `__ldcs` (non-temporal) loads on the warp-row weight/scales
regressed the aggregate 812 -> 769 GB/s (the L2 policy change hurt the
activation/scale reuse) — reverted.

**Rejected**: a whole-sequence decode CUDA graph (capture all
`max_new` steps with each step's `kv_base` baked into fixed nodes, replay
once; `LSX_GRANITE_GRAPH`-style). Bit-exact vs the host loop on the synthetic
fixture, but at `max_gen=2048` it captures ~2047 x 253 = ~518k nodes and
measured 21.49 t/s vs the host loop's 25.36 (**-15%**): per-node replay
overhead exceeds the launch tail it removes. Reverted. The viable graph form
is a **single-step graph** (253 nodes) replayed once per token, which needs
the decode step to read `kv_base` from a device scalar (attention bound and
the KV-store offset become device-driven) — that plumbing is the next attempt,
not the whole-sequence bake.

**Next levers** (not done here): (2) fuse q/k/v (and gate/up already fused)
into one wider streaming GEMV to cut launches and lift the N=4096 shapes'
occupancy; (3) split-KV decode attention for long context; (4) seq==1
RMSNorm (grid=1 block, ~6% at short context).

## Perf findings — lever #1b (activation-load vectorization)

A single-step decode CUDA graph (device-driven `kv_base`, 253 nodes, replayed
per token) was implemented and validated bit-exact on real weights, but gave
only +0.8% perf / +0.5% r3 — the GPU is ~98% busy and the launch tail is
already hidden. Reverted.

Diagnostic probes on the RTX 5090 (gate_up K=4096 N=65536):

| probe | GB/s |
|---|---|
| raw streaming read (`__ldg`) | 1618 |
| warp-per-row weight access pattern, no math | 1534 |
| E2M1 decode + FMA, no activation x | 1182 |
| E2M1 LUT decode, no x | 1126 (worse: divergent L1 gathers) |
| x loads + FMA, no decode | 925 |
| full GEMV (before) | 878 |

So the gap to DRAM is **activation-load instruction pressure**, not decode.
Fix: force four 128-bit activation loads per 32-element weight chunk and use
`__half22float2` in both the sliced and warp-row kernels. Isolated aggregate
**873 -> 918 GB/s** (+5%); E2E 25.36 -> 25.71 t/s (+1.4%), r3 17.76 -> 17.91.
Row-pairing (2/4 rows per warp) was tried and regressed (register pressure) —
rejected.

nsys at 64 tokens (33.5 t/s) shows the in-situ kernel split: warp-row gate_up
50.8%, sliced KP=8 down 25.7%, sliced KP=4 q/k/v/o 11.0%, RMSNorm 7.2%,
attention 2.3%. In-situ GEMV rates are 630-740 GB/s vs 918 isolated (the
interleave/cold-L2 penalty), and the small q/k/v/o launches run at ~184 GB/s
(latency-bound).

## Perf findings — lever #2 (fused q/k/v projection)

The converter now quantizes q/k/v JOINTLY into one
`self_attn.qkv_proj.weight` record ([NH*HD + 2*NKV*HD, K], single global
scale), mirroring the existing gate_up fusion. The loader exposes q/k/v as
non-owning row-slices; the decode step runs ONE GEMV then a split kernel.

Effect: the fast-math path (perf) 25.71 -> 26.02 t/s (+1.2%), but the
**bit-exact r3 path 17.91 -> 25.96 t/s (+45%)** — in kOff mode q/k/v had been
three separate scalar tile GEMMs, the two tiny N=1024 ones latency-bound;
one fused [6144, K] tile GEMM removes that. r3 is now on par with perf.
Selfcheck Paris x3 remains bit-exact (joint quantization shifts the hash, as
expected). Synthetic convert/loader/model tests updated for the new record.

**Hard ceiling**: NVFP4 is 0.5625 B/param (4-bit + 1 E4M3 per 16). A dense
29B reads 16.2 GB/token; at the measured 1618 GB/s raw ceiling that is
10.0 ms = **~100 t/s even at 100% HBM**, ~73 t/s at the 1182 GB/s
math-inclusive limit. `>100 t/s` is therefore not reachable for this dense
model on this GPU; the practical target is 40-70 t/s via in-situ scheduling
and the small-kernel/attention levers above.

## Perf findings — lever #3 (split-KV / flash-decoding attention)

nsys at `--max-gen 2048` (full 62 s trace, kernel time == wall within 1.2% so
there are no launch gaps) re-attributed the decode wall *after* levers #1/#1b:

| kernel | share | us/call |
|---|---|---|
| warp-row GEMV (gate_up + head) | 39.8% | 234 |
| **granite_attn (single block/row)** | **26.5%** | **158** |
| sliced GEMV KP=8 (down) | 20.1% | 120 |
| sliced GEMV KP=4 (qkv/o) | 7.2% | 21 |
| RmsNorm | 5.5% | 16 |

Attention reads only ~8.4 MB/layer/token at ctx 2048 (0.33 ms/token across all
layers) yet cost 10.1 ms/token — ~30x above its KV-read bound. Cause: the
kernel launched `seq*nh` blocks, i.e. **only 32 blocks at decode (seq==1)** on
a 170-SM part, and the inner loop is a 128-deep serial FMA chain over scalar
`__half` K/V loads.

Fix: split the causal key range `[0, kv_base+t]` across `kAttnSplit=8`
contiguous blocks (grid `(seq*nh, splits)`), each emitting an online-softmax
partial `(m, l, o)`; `granite_attn_combine_kernel` merges the partials in fixed
split order. Fixed boundaries + fixed merge order keep the path run-to-run
deterministic. Dispatch only for `seq <= 8` and `kv_base+1 >= 256` (long-seq
prefill already has `seq*nh` blocks of its own); the partial slab is sized for
the decode regime in `Workspace`.

Effect: attention **20.74 s -> 3.88 s** (26.5% -> 6.2% of the wall, 158 -> 30
us/call, ~5.3x), E2E **26.02 -> 32.93 t/s (+27%)** reproduced twice; r3 25.96 ->
32.83. Verified by a forced-split-vs-CPU-reference parity test (8330
assertions), `test_granite_dense_selfcheck` Paris x3 (hash unchanged, the 6-token
prefill stays on the unsplit path), `ctest -L fast` (55/55) and the granite
guard suite.

## TMA (Tensor Memory Accelerator) status and the remaining GEMV gap

TMA is **already in use**, but only on the tensor-core (prefill / seq>1) route:
`lsx_tc_gemm.cu` encodes a cached `CUtensorMap` per weight tensor and stages
`cp.async.bulk.tensor.2d` tiles behind an mbarrier (plus a `cp.async` fallback
and a bulk-tensor capability probe). The seq==1 decode GEMV — which is now
~85% of the decode wall — deliberately does *not* stage through shared memory
(`lsx_inference_nvfp4.cu`: "no shared-memory slab, no MMA, no cp.async
pipeline"), because an earlier tile/MMA decode experiment showed smem staging
throttling a single-activation-row GEMM.

## Perf findings — lever #4 (branchless E2M1 decode) — the big one

After lever #3 the GEMV was ~85% of the wall but ran at only ~620-646 GB/s
in-situ, against ~926 GB/s for the same kernels in the isolated harness. That
gap was chased to ground with a direct experiment that loads the **real**
`logestix-granite` weights into the test:

| probe (same kernel, shape, x, stream) | GB/s |
|---|---|
| synthetic uniform packed (old code) | 933 |
| **real packed weights (old code)** | **655** |
| real packed + synthetic scales | 657 |
| synthetic packed + real scales | 928 |
| D2D copy of the real packed bytes into a fresh buffer | 656 |
| synthetic resampled from the real byte histogram | 658 |

So it was the **packed weight data itself**, not scales, not buffer placement,
not the footprint, not the stream, not throttling (a sustained 20 000-iteration
isolated run stays at ~930).

Root cause: `nvfp4_codec.h::E2M1Value` was a `switch (mag)` — the compiler
emitted a **data-dependent indirect branch**, so throughput depended on the
nibble distribution (uniform synthetic vs real weights: 30% apart). Replacing
it with a branchless form (the 8 magnitudes packed as 2*value nibble codes
`{0,1,2,3,4,6,8,12}` in `0xC8643210`, `code * 0.5f` is exact in fp32) is
**bit-identical** (guarded by `test_lsx_kernels.cu`'s exhaustive E2M1 table;
granite's selfcheck logits hash is unchanged) and lifts *both* cases:

- isolated read-flush: real 655 -> **1594**, synthetic 933 -> **1598** GB/s
- the memset-flush budget harness: aggregate 900 -> **1327** GB/s (gate_up
  906 -> 1336, down 858 -> 1306, head 934 -> 1369, q_o 576 -> 764)

The kernel now sits at ~98% of the measured ~1618 GB/s raw read ceiling, so the
earlier "918 GB/s isolated" figure was itself a switch artefact, not a hardware
limit. **TMA/smem staging for the decode GEMV is therefore unnecessary**: the
warp-row kernel already issues only ~4 coalesced 16-byte weight loads per lane
per row and is now bandwidth-saturated, so a gmem->smem->reg round trip would
only add traffic. (TMA remains in use where it fits — the tensor-core prefill
route in `lsx_tc_gemm.cu`.)

This is a *shared codec* change: every decode path in the repo (qwen, gemma,
glm, kimi, deepseek, granite) calls `E2M1Value`, so the win is repo-wide and
the bit-identity check is the correctness gate.

E2E Granite-4.2-30B @ 2048: **32.93 -> 65.07 t/s** (perf, reproduced
65.1/65.0/64.9), **32.83 -> 64.26 t/s** (r3); selfcheck Paris x3 bit-identical;
`ctest -L fast` 55/55.

### Remaining levers

With the GEMV at ~66% of the wall and near the DRAM ceiling, the next targets
are the non-GEMV 34%: RmsNorm (~2.1 ms/token; the seq==1 launch is a grid=1
block) and split-KV attention (~1.9 ms/token). The hard ceiling is unchanged:
~16.2 GB/token over ~1618 GB/s = 10.0 ms/token GEMV-only, i.e. ~100 t/s in the
limit, ~73 t/s at the 1182 GB/s decode+FMA bound.
