## Publish-ready post

### Notes from an independent NVFP4 port of Beam-1.0-501B-A23B

We integrated Beam into our own C++/CUDA inference engine (no PyTorch at
runtime) and converted the BF16 release in place to NVFP4: 934 GB of
safetensors → a ~265 GB tree, with the 12,544 routed experts streamed from host
mmap through a device-slot LRU. The dense graph pins at 6.49 GiB; with a
512-slot expert cache the process sits around 17.4 GiB of VRAM on a single
RTX 5090. Thanks for shipping the reference `modeling_beam.py` in
`transformers` — it made the architecture unambiguous.

#### What worked well

- Greedy determinism is solid: the framed control prompt answers "Paris" with
  the analysis/final channels, and three runs produced byte-identical final
  logits.
- The native tool wire is unambiguous and easy to parse: `to={name}` +
  `<|channel|>analysis <|constrain|>xml<|message|>` + `<rfl:parameter name="…">`
  bodies. A real-weight round-trip returned `get_weather {"city":"Paris"}`.
- The Harmony markers being `special: false` added tokens is the right call —
  they encode literally and survive detokenization. (Runtimes that only match
  `special: true` tokens will break the framing, so it is worth stating this in
  the model card.)
- The per-head attention gate (with its `[48]` bias), the depth-scaled residual
  (`idx = 2(l+1)`), the four sandwich norms and the NoPE + SSMax full-attention
  layers all behave as documented once implemented exactly.

#### Two artifact-level issues worth fixing or documenting

1. **`config.json` has `"eos_token_id": null`; the real stop list lives only in
   `generation_config.json` as `[151674, 151675]`.** A runtime that reads just
   `config.json`, or takes only the first id, gets `<|return|>` and misses
   `<|call|>`. The failure mode is nasty: after a tool call the model does not
   stop and repeats the call indefinitely. Merging both files (or duplicating
   the list into `config.json`) would make this robust.

2. **`vocab_size` is 151,936 but the tokenizer's highest token id is 151,680.**
   Sampling can therefore produce ids in `151681..151935` that have no
   tokenizer bytes. If a detokenizer treats one unknown id as a fatal error
   (ours did), a perfectly valid tool call disappears from the decoded stream.
   We now drop out-of-vocabulary ids before decoding, but it would help to
   document that this range is reserved/undefined — or mask it in the reference
   sampler.

#### Things that were easy to get subtly wrong (for anyone porting)

- Full-attention layers are genuinely NoPE; the position information comes only
  from the SSMax query scale `(1 + (pos+1)/2048)^0.1`.
- The router must keep the correction bias for **selection** but renormalize the
  **plain** sigmoid scores, then apply `routed_scaling_factor` (2.5) after
  aggregation. There is no shared expert.
- `norm_topk_prob`, the group-limited top-2-per-group score and the top-4 group
  mask all matter; a small deviation silently changes the expert set rather
  than degrading smoothly.
- The sliding window is 512 tokens **including** the current one.

#### Quantization notes

At 4-bit on all projections plus FP16 `embed_tokens`/`lm_head`, FP16 norms and
an FP32 router, the control prompt and tool call are correct and deterministic.
The remaining error is dominated by the routed-expert 4-bit plane. We could not
run FSI/CODE/DET-style parity captures here because the 934 GB BF16 source does
not fit in 750 GB of host RAM, so we validated at the kernel level against a
host reference instead. If the authors have a recommended NVFP4 recipe (or a
list of tensors that must stay high precision), it would be very useful to
publish it.

#### One data point on speed

Our correctness-first path (token-by-token prefill/decode, no CUDA graphs, a
router readback per MoE layer) reaches **1.61 t/s at 2048 generated tokens**
(TTFT ≈ 27 s) on the RTX 5090, with the expert stream as the bottleneck. That is
a floor, not a verdict on the model's throughput — it mostly measures our
host-to-device staging.

Overall: a very clean architecture to port, and the two stop-id/vocab-range
details above are the only things that cost real debugging time. Thanks for the
release.

### What the checkpoint forced into the engine

1. **Gated GQA** — `self_attn.gate_proj` plus one bias per head; `attn_out *=
   sigmoid(gate + bias[head])` before `o_proj`.
2. **Four sandwich norms + depth-scaled residual** — `idx = 2*(layer+1)` for
   attention, `idx+1` for the MLP; each scaled operand rounded before the add.
3. **Hybrid attention** — 43 sliding layers (rotate-half RoPE, full 128 dims,
   theta 10000, window 512 inclusive) and 9 full layers {5,11,…,47,51} with
   NoPE + SSMax.
4. **Group-limited sigmoid router** — FP32 logits, bias for choice, top-2-sum
   per group, top-4 groups, top-8, plain sigmoid renormalized, ×2.5 after
   aggregation; no shared expert.
5. **Final logit softcap 30**, SwiGLU product in FP32, per-head q/k RMSNorm.
6. **Tokenizer** — Qwen2/3 single-run pre-tokenizer (one digit per number word,
   no case/CJK split) with the Harmony markers as plain added tokens.
7. **Modified Harmony wire** — `analysis`/`final` channels, `to={name}` +
   `<constrain|>xml` + `rfl:parameter` bodies.

### Defects found on real weights (fixed)

- **Lost second stop id** — `config.json`'s `eos_token_id` is null and the real
  list is in `generation_config.json`; reading only the first id (`<|return|>`)
  left `<|call|>` (151675) unhandled, so the model repeated a tool call forever.
  Fixed by carrying the full list through the converter/index/loader/model.
- **Reserved-id decode failure** — one sampled id above the tokenizer's maximum
  made the whole token-stream decode fail, hiding a valid native call. The
  parser now drops out-of-vocabulary ids before decoding.
