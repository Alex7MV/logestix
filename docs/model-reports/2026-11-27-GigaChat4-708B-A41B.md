**Verdict at a glance:** GigaChat4-708B-A41B — 710 B total / 41 B active, the
64-layer sibling of the already-shipped 37B (same code, 19× the parameters):
GatedDeltaNet on 48 layers, DSA-sparse gated MLA on 16, and a 256-expert top-8
MoE on 61 layers. It runs on a single consumer RTX 5090 at **3.71 tokens/s** at
the canonical 2 048-token protocol (TTFT 11.1 s), with the entire 361 GB expert
set streamed from locked host memory — 488 expert touches and ~12 GB of PCIe
traffic per token. SelfCheck is bit-exact across three cycles
(`logits_hash 4c91393c68d0b3e8`, top-1 `Paris`), CODE is 3/3, and FSI/DET are 2/3
each where the single red case in each is the answer-extraction layer picking a
reasoning preamble line instead of the model's (correct) final answer — a
recorded instruments defect, not a model defect.

## Publish-ready post

### GigaChat 4 708B-A41B on one RTX 5090

We ported Sber's GigaChat4-708B-A41B — the large sibling of the 37B we shipped
last week — into the same Blackwell inference engine. The architecture is
identical (the modeling code, tokenizer and chat template are byte-for-byte the
same files), so the interesting part of this ingestion was not the math: it was
that a 710-billion-parameter model with a 361 GB 4-bit expert set has to live
almost entirely in host memory on a 32 GB card, and the engine had never run
that path at this scale.

**What it costs.** Each decoded token routes to 8 of 256 experts in each of 61
MoE layers — 488 expert matrices, about 12 GB — so decode is a PCIe exercise,
not a compute one. The card holds 389 expert slots out of 15 616, a 2.5 % hit
rate, and the model settles at **3.71 tokens/s** with an 11.1 s first token at
power that never exceeds 155 W. For comparison the 37B, whose whole expert set
fits on the card, does 63 t/s.

**What the checkpoint forced into the engine.**

1. **Everything is the 37B's semantics at a new width.** The one trap is that
   the frozen geometry cannot be inherited: `alpha_q = √(7168/1536) = 2.1602`
   and `alpha_kv = √(7168/512) = 3.7417`, against the 37B's 1.2910 and 2.2361.
   Every width changes too — 64 layers instead of 32, 61 MoE layers instead of
   31, 256 experts instead of 192, a 2048-wide expert instead of 768, and 32/64
   GDN heads instead of 16/32. A single constant left behind still produces a
   model that answers, with the wrong arithmetic; our test suite swaps the
   alpha back to the 37B value and fails.
2. **Allocation order.** The expert slot cache sizes itself from free VRAM minus
   a 4 GiB reserve, and this model's MLA KV cache is 5 GiB at a 4096-token
   session. Sizing the cache first therefore left the KV allocation to fail and
   the load aborted after two minutes of pinning 361 GB of host memory. Fixed
   allocations now come first and the elastic cache is sized against what is
   actually left.
3. **Conversion memory.** Holding every routed expert in one in-memory map is
   19.7 GB on the 37B and 387 GB here. The converter now flushes a layer's 256
   experts to disk and releases them before reading the next layer, so the
   working set is one layer regardless of model size.

**A real defect found on the way — and it was in the long-context path.** The
sparse attention indexer takes the RoPE tables and selects its own row for the
current position. The decoder was handing it an already-advanced pointer, so
every index query and cached key was rotated by twice the position. Below 2 048
tokens this is invisible, because the indexer's selection is the identity there
— which is exactly why every short-context gate on the shipped 37B was green.
Above it, the selection was scored from wrongly rotated keys, and past position
2 048 the doubled offset read past the rope table (compute-sanitizer flagged it
as an out-of-bounds read on the 708B's longer prompts). One call site; the
regression test compares the decoder's cached key against the indexer driven
directly at the same position, so it pins behaviour rather than a tolerance.

**What we did not measure, and why.**

- The FSI/CODE/DET goldens are template-derived. Executing the source means
  dequantizing 720 GB of FP8 to ~1.4 TB of BF16, which does not fit 750 GB of
  RAM here; source-side agreement instead rests on the per-layer probe against
  the reference implementation that the 37B ingestion built (per-stage cosines:
  0.997 on the layer residual, bounded by the 4-bit quantization floor).
- No long-document evaluation at the 1 M-token window the config declares: the
  session cap is 4 096 (the KV cache is 5 GiB there) and DSA above 2 048 keys is
  exercised by the kernel tests and by the 2 048-token perf run.
- MTP (the checkpoint's own single prediction layer) and the shipped
  `dflash_draft` drafter are stored and counted, never applied.
- Batch > 1, multi-GPU and tensor parallelism are out of scope for this card.

#### Notes for the model authors

1. `config.json` still declares `"use_cache": false` while the architecture is
   stateful and `max_position_embeddings` is 1 048 576 — three fields that
   disagree about whether the model is used with a cache.
2. `quantization_config.ignored_layers` is not a reliable precision classifier:
   it omits `self_attn.indexer.wq_b`, the one indexer tensor stored in FP8. The
   per-tensor `weight_scale_inv` sibling is the only trustworthy signal.
3. The chat template's `reasoning` default is `True`. This model then writes a
   numbered analysis preamble that *paraphrases the prompt* before answering. It
   is worth knowing for anyone automating extraction: the answer is the last
   line, and formulas are sometimes wrapped mid-expression.

The two reds are the **`I3` instruments item**
(`docs/open-tasks/live/instruments-and-guards.md` §I3): both extractors are
shared by all 43 manifests, so repairing them requires its own before/after
sweep and is deliberately not bundled into a model ingestion. In both cases the
model's own raw text contains the correct answer.
