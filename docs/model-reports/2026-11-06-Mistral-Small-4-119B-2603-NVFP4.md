## Publish-ready post

### Notes from a second NVFP4 port of Mistral-Small-4-119B-2603

We run Mistral's 119B small model in our own C++/CUDA inference engine (no
PyTorch at runtime). The released checkpoint is already NVFP4-quantized in the
Mistral "consolidated" layout — `params.json` plus 13 shards, no `config.json` —
so it converts in place to a 66 GiB tree in about 76 seconds: 4.4 GB of
attention/norm/embedding weights stay device-resident as BF16 and the 4 608
routed experts are memory-mapped from the host and streamed per token through a
card-sized LRU. On one RTX 5090 it loads in about a second and decodes at 45.8
tokens/s at 2 048 tokens.

The architecture is DeepSeek-V2-style MLA — q/kv latent compression, 32 heads at
64 NoPE + 64 rotary dims, 128-wide values — combined with a 128-expert top-4 MoE
plus one shared expert on **every** layer, YaRN scaling at factor 128 over an
8 192-token original window, and a Llama-4 logit temperature.

#### What worked well

- **Determinism is solid.** Three independent runs of the control prompt produce
  byte-identical full-vocabulary logits (131 072 values) and the same top-1.
  The routed experts stay in their original NVFP4 encoding — the converter
  repacks nothing — so no accuracy is spent on a second quantization.
- **The tool wire is unambiguous.** The template's
  `[TOOL_CALLS]name[ARGS]{json}` markers are parsed without heuristics; a
  real-weight round-trip produced the `get_weather` call with
  `{"city": "Paris"}`.
- **Streaming and cancellation come for free** through the engine's shared
  lifecycle contract: one token event per decoded token, and a pre-set abort
  flag stops the request instead of running out the budget. Pinned by
  `test_mistral_moe_model` on the family's **synthetic** fixture (2 layers) —
  it exercises the wiring, not the 66 GiB checkpoint, which is why this model
  does not carry the selfcheck driver's `cooperative_cancel` hook: the coverage
  already exists at the model stage, and the old per-family selfcheck never had
  a cancel case to lose.

#### Checkpoint facts that are easy to get subtly wrong

1. **The source is *already* quantized, and its global scale is a divisor.**
   `weight_global_scale` follows compressed-tensors semantics
   (`w = nibble · block_scale / weight_global_scale`), which is the inverse of
   the convention most NVFP4 toolkits store. Multiplying instead of dividing
   produces a model that answers — with the wrong numbers.

2. **The activation-only `input_global_scale` companions are not weights.** They
   describe input quantization; treating them as tensors to convert inflates the
   memory estimate and, if used as a scale, silently rescales activations.

3. **The KV cache holds the latent, not per-head keys and values.** With MLA the
   cache row is `kv_lora_rank + qk_rope_head_dim` = 320 values, not
   `heads × head_dim`. Sizing it the naive way over-allocates by ~13x here and
   makes a 1M-token context look impossible.

4. **`apply_scale` is false, so the YaRN tables must not be pre-multiplied.**
   The attention factor is folded into the softmax scale only; scaling the
   cosine/sine tables as well double-counts it.

5. **The Llama-4 logit temperature is position-dependent.** The factor
   `1 + 0.1·log(⌊pos/8192⌋ + 1)` applies to attention logits beyond the original
   window; it is not a constant and not a final-logit soft cap.

6. **Every layer is MoE — there is no dense prefix.** `first_k_dense_replace`
   is 0, so a converter that assumes a dense first layer misassigns an entire
   layer's weights.

7. **The vision tower ships in the same shards.** 222 tensors
   (`vision_encoder.*`, `patch_merger.*`, `pre_mm_projector_norm.*`) belong to a
   multimodal front end. Strip and count them; do not let them reach the text
   decoder.

8. **There is no `config.json`.** Any tool that requires one must be fed a
   synthesized config, and `params.json` uses different field names
   (`dim`, `n_layers`, `hidden_dim`, `moe.expert_hidden_dim`). Note that
   `hidden_dim` here is the *dense MLP* width (12 288), not the model width.

#### Suggestion to the model authors

Ship a `config.json` alongside `params.json` — even a minimal one with
`model_type` and `architectures` — and state in `params.json` that
`weight_global_scale` is a divisor. As it stands, the only way to know which
convention applies is to read `compressed-tensors` source, and the only way to
load the checkpoint in Transformers is to reconstruct the config by hand.

#### The throughput rows do not reproduce, and it is not thermal (2026-11-07)

Re-running `test_perf_baseline_mistral_small_4` on the same tree eleven days later,
six times, both modes:

```
perf  43.98  44.26  44.31  44.20  44.23  43.89   -> 95.9-96.8% of 45.77
r3    (was not measured until the harness fix below)  47.99 -> 96.3% of 49.82
```

Stable to under 1% across runs, and stable across **both** modes, so it is a
systematic ~4% difference from the recorded reference rather than noise. The
temperature hypothesis was tested directly — cold card versus immediately-rerun hot
card — and is disproven:

| | cold (45 °C start) | hot (straight after) |
|---|---|---|
| temperature | 46.4 mean / 51.0 max | 46.5 mean / 51.0 max |
| SM clock | 1822 MHz mean | 1879 MHz mean |
| board power | 142.5 W mean / 240 W max | 145.3 W mean / 241 W max |
| verdict | DEGRADED | DEGRADED |

The card never exceeds 51 °C and never exceeds 240 W against a 600 W cap, so neither
thermal nor power throttling is involved; the harness's own DRAM oracle agrees
(1524 vs 1533 GB/s, 99.4%). Nothing in `mistral_moe_*` or the shared kernels changed
since the baseline date, and `granite-4.2-30b` shows the same shape (96.7%) while
`phi-4` passes.

**What this is not settled as:** a code regression cannot be excluded, so the
reference has deliberately **not** been re-seeded — the harness forbids it for a
DEGRADED verdict and doing so would erase the only evidence if it is real. Two
candidate causes are recorded in `docs/OPEN_TASKS.md` §G8: the reference is a
ratcheted best-of sample (this row replaced 45.04, and `r3` replaced 41.57 — a 20%
jump, itself a sign of an unstable measurement), and the entry predates the
`expert_cache_slots` field, so the capacity oracle cannot fire for the family most
sensitive to it (4 608 routed experts streamed through 1 398 device slots, and the
capacity is derived from ambient free VRAM). Treat both throughput numbers above as
the 2026-11-06 measurement they are, not as a reproducible constant.

#### Not measured, and why

The three answer-parity gates (a financial-formula set, a compiler-syntactic
code set, and a determinism/near-tie set) were **run** on this tree with
goldens derived from the prompt sets, and they do not pass: **FSI 1/3,
CODE 0/3, DET 0/3**. DET reports `deterministic=true` on all three prompts with
three byte-identical runs each, so the failure is answer *format*, not
instability: the model is coherent and on-topic, answers the third financial
formula exactly, and reproduces the same "reasons to the answer without emitting
the token" behaviour this checkpoint showed on its first ingestion.

These goldens are **not committed and the gates stay declared debt**, because a
prompt-derived expected value cannot establish parity — it would assert only
that the converted path agrees with a template, which the control-prompt check
already covers more cheaply, and three permanently-red targets train people to
ignore red. A consequence worth stating plainly: **the three fractions above
cannot be re-derived from this repository.** Re-running the targets today reports
`Skipped` (verified 2026-11-07, exit 4, golden absent), so a reader who wants to
check 1/3 / 0/3 / 0/3 has to re-capture prompt-derived goldens locally first — at
which point they are checking the capture script, not the model. The numbers are a
dated measurement, and the durable evidence for this model is SelfCheck (bit-exact,
hash pinned) plus the tool round-trip, both of which run from the vault. A source-faithful golden needs a reference run of the checkpoint,
and that is blocked: the reference model class now exists and its defaults match
this checkpoint, but the checkpoint's tensor **names and expert layout** do not
match it (50 missing / 3118 unexpected parameters; experts stored per-expert
rather than fused), so a plain load runs a randomly-initialized model. The
capture tool refuses such a model by construction rather than producing a golden
from random weights.

Two harness defects were found and fixed while running these gates: the FSI
capture script had no framing override for this model and never applied the one
it reads, so its first run measured 0/3 purely from a vendor system prompt that
the engine does not send.
