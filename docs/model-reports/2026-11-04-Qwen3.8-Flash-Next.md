**Verdict at a glance:** green on every parity gate with real weights —
SelfCheck "Paris" ×3 with byte-identical full-vocabulary logits
(`logits_hash = 2e3bcd090441ad65` over 248 320 logits, top-1 id 11751), FSI 3/3,
CODE 3/3, DET 3/3 (3 byte-identical runs per prompt), the family's EOS and
cross-instance determinism gate, and a native tool round-trip that emits
`<tool_call><function=get_weather><parameter=city>Paris</parameter></function></tool_call>`
and parses to `{"city":"Paris"}` in 26 generated tokens. Throughput at the
canonical 2 048-token protocol is **42.98 t/s** (`perf`, auto policy) and
**33.88 t/s** (`r3`, strict bit-exact) — and it is a *capacity* number, not a
compute number: at 5 350 resident expert slots the hit rate is 0.86 and ~300 MB
of experts are streamed per token, so the decode rate tracks free VRAM almost
linearly (5 750 slots → 44.15 t/s; 6 000 slots does not allocate on this card).

The architecture is a hybrid decoder: 48 layers in 12 blocks of three
GatedDeltaNet (linear-attention) layers followed by one QSA full-attention layer
with a sparse indexer, hyper-connections (four residual streams) instead of a
plain residual, a 512-expert top-10 MoE on every layer, and an n-gram embedding
(PLE) injected at layer 2. The routed expert set is the model: 64 GB of NVFP4
arrows, 2.7 MB per expert, and every token touches ten of them across every
layer.

## Publish-ready post

### Notes from an independent NVFP4 port of Qwen3.8-Flash-Next

We run Qwen3.8-Flash-Next in our own C++/CUDA inference engine (no PyTorch at
runtime) on a single RTX 5090. The 336 GB BF16 release converts in place to a
164 GB tree. Only a 3.6 GiB dense graph is device-resident; the 24 576 routed
experts live in a 63.6 GB pinned host arena and are streamed per token through a
device slot cache, and the 96 GiB n-gram table is memory-mapped and read a page
at a time. Load takes about 50 s (the arena build dominates), and decode runs at
42.8 tokens/s at 2 048 tokens.

#### What worked well

- **Determinism is solid.** The control prompt answers "Paris", and three
  independent runs produce byte-identical full-vocabulary logits. A second model
  instance in the same process answers identically, which matters here because
  the expert-residency bookkeeping is process-lifetime state.
- **All four of our parity gates pass on real weights**: a financial-services
  formula set (3/3), a compiler-syntactic code set (3/3), a determinism/near-tie
  set (3/3), each captured from the source weights rather than from a template.
- **The tool wire is unambiguous.** The template's
  `<tool_call><function=NAME><parameter=K>V…` XML is parsed without heuristics,
  and a real-weight round-trip produced the `get_weather` call with
  `{"city":"Paris"}`. One template delta over the earlier Qwen 3.x checkpoints
  (the closed think block on assistant history turns) plus this member's own
  `preserve_thinking` and empty-system-turn defaults had to be reproduced
  byte-for-byte (see below) — with them, multi-turn and tool turns frame exactly
  as the checkpoint's own Jinja template does.
- **4-bit is enough for this checkpoint.** Unlike some models we have ported, the
  body tolerates NVFP4 throughout — with two deliberate exceptions, the LM head
  and the n-gram table (below). No residual weight plane was needed.

#### Checkpoint facts that are easy to get subtly wrong

1. **The LM head must not be quantized.** At 4 bits the logit noise is ~0.5,
   which exceeds this model's typical top-1/top-2 margin; the argmax flips. We
   keep `lm_head` in BF16 (an extra 1.2 GB) and quantize everything else,
   including the embedding table.

2. **There are three distinct model-type names.** The top level is
   `qwen4_exp`, the text sub-config is `qwen4_exp_text`, and the architecture is
   `Qwen4ExpForConditionalGeneration` — with `language_model_only: false`
   because the release still ships a 333-tensor vision tower. A loader that keys
   on one name silently skips or misclassifies the other. We strip and count the
   vision tower (`skipped_visual_tensors: 333`).

3. **The EOS ids disagree between files.** `config.json` says `248044`,
   `generation_config.json` says `[248046, 248044]`, and `tokenizer_config.json`
   names `<|im_end|>` as the EOS token. Reading only the config makes the model
   run to the token budget whenever it ends with `<|im_end|>` — the common
   ending. We take both ids. *(Suggestion to the authors: make `config.json`
   authoritative and consistent with `generation_config.json`.)*

4. **`pad_token_id` is `null` in the text config while the tokenizer pads with
   `248044`, which is also the secondary EOS.** A padded batch therefore looks
   like a batch that stopped. We never batch, but an implementer who does will
   find this quickly. *(Suggestion: ship a pad id that is not a stop id.)*

5. **`rope_parameters.mrope_interleaved: true` with `mrope_section [11,11,10]`
   is the multimodal branch.** The text decoder rotates 64 of its 256 head dims
   with a plain rotary table (θ = 1e7); applying the M-RoPE sections to text
   positions corrupts them. If you only run text, ignore that block. *(Suggestion:
   document which sub-block the text path consumes.)*

6. **`ple_layer_ids: [2]` but the tensors are `layers.1.ple.*`.** One is
   1-based and the other 0-based. Getting it wrong either fails to find the
   table or injects it into the wrong layer; the model still produces fluent
   text, which is the worst failure mode. We gate the converter on
   `ple_layer_ids == [layer_idx + 1]`.

7. **The n-gram (PLE) table is 96 GiB of BF16 in 128 shards — larger than every
   other weight in the model combined.** It must be memory-mapped and gathered
   per token, not loaded. *(Suggestion: a quantized or int16 copy would cut the
   tree by ~40 %.)*

8. **`generation_config.json` samples by default** (`do_sample: true`,
   `temperature 1.0`, `top_k 20`, `top_p 0.95`). Any parity work has to pin
   greedy explicitly, exactly as we do.

9. **MTP is declared but inert**: `mtp_num_hidden_layers: 1`, `mtp.hybrid`,
   `mtp_use_hidden_state_from_layer: null`. We convert and count it under
   `deferred` and never apply it.

10. **The decode working set is the whole expert set.** 512 experts at
    intermediate 640 per layer × 48 layers means each expert is only ~2.7 MB,
    but a token touches ten of them per layer, and the union over a decode run
    is effectively all 24 576. A bounded LRU over file-backed mmaps measured
    9.2 tokens/s against the pinned arena's 32 on the same card; pinning the
    whole set is the only thing that pays here. Budget host RAM for it.

#### What we did not run

- **The 262 144-token window.** We verified short/medium prompts and the
  2 048-token protocol; the full window's KV and recurrent state exceed this
  card, and the expert-cache capacity is already the limiting factor.
- **MTP / speculative decoding** — the layer is stored (counted) but never runs.
- **Any multimodal path** — the vision tower is stripped; this is a text-only
  port.
- **Sampling quality.** All parity numbers are greedy; the sampler is wired but
  the checkpoint's own `do_sample` defaults were not benchmarked.

Overall a well-specified checkpoint once the three traps above are known
(LM-head precision, EOS id disagreement, and the PLE index base). The one thing
that cost real time was the capacity behaviour: throughput moves 10-30 % with
expert-cache size, so a "regression" here is usually less VRAM, not slower code.

### Stage 4b — the 3.8 template differs from 3.5/3.6 (found TDD, corrected later)

The shared Qwen codec was written for the 3.5/3.6 `chat_template.jinja`.
Rendering the 3.8 template (transformers 5.15.1,
`apply_chat_template(..., enable_thinking=False)`) for the same conversation
showed three deltas from the wire the engine emitted:

1. every **assistant history** turn carries the closed think block
   (`assistant\n<think>\n{reasoning}\n</think>\n\n{content}`), even with thinking
   disabled and an empty trace — we rendered `assistant\n{content}`;
2. tool definitions serialise like jinja `tojson`
   (`json.dumps(obj, ensure_ascii=False)`: `", "` / `": "` separators), not
   compact;
3. every message body goes through `render_content(...)|trim`.

A new `QwenRenderPolicy` carries them, and the new cases in
`tests/test_qwen_tool_framing.cpp` assert against the **template output**, not
against our renderer. All were written red first. A third case
(`tests/test_qwen_moe_exp_model.cpp`) pins the whole policy the model renders
with, flag by flag: the first version of this change covered `trim_content` in
the renderer test and then left it off for the actual model, which is precisely
the defect a per-flag renderer test cannot catch.

**Correction, same day.** Deltas (2) and (3) turned out **not** to be 3.8-only:
`diff` against the 3.6 template shows the `|trim` sites and the
`{{- tool | tojson }}` line identical, and all six checkpoints carry 4 trim sites
+ 1 tojson site. So the deviation was family-wide (the compact JSON and the
untrimmed content affected every qwen member), and 3.8 additionally trimmed tool
names/descriptions that its template renders verbatim. Fixed on branch
`fix/qwen-template-fidelity` (`b3eaa066`): both flags deleted, trimming and
tojson made unconditional, trim scoped to message content,
`suppress_empty_system` added as the one further 3.8 delta, four oracle-pinned
cases added, and real-weight tool round-trips added for the two members that had
none (qwen3.5-9b, qwen3.5-35b-a3b). All six round-trips green on the new wire,
every `logits_hash` unchanged, `ctest -L fast` 134/134 —
[`docs/open-tasks/2026-11-04-qwen-template-fidelity.md`](../open-tasks/2026-11-04-qwen-template-fidelity.md).

### Two perf-harness defects found and fixed (TDD)

Neither is a model defect; both were under-reporting the whole perf suite and
both were invisible because the numbers "looked plausible".

1. **The bandwidth probe leaked 1 GiB of VRAM for the process lifetime.**
   `MeasureMemoryBandwidthGbs` held its two 512 MiB buffers in `thread_local`
   statics. `test_perf_baseline` runs the probe before the model, so every
   capacity-bound family measured with 1 024 MiB less free VRAM than the card
   had, hence fewer expert slots and a low reference. Measured here: 4 962 →
   **5 350** slots. Pinned by
   `TEST_CASE("memory-bandwidth probe releases its device buffers")`
   (`test_gpu_perf`, 86 assertions / 15 cases).

2. **The generation scratch was charged twice on the second `Load()`.**
   The generation arena and fp16 embed table are process-lifetime statics; the
   harness runs `perf` then `r3` as two loads in one process, so the second load
   subtracted the first leg's 5 581 MiB reserve from VRAM it had already paid
   for. Fixed with `SizeExpertCacheSlots(..., already_resident_bytes)` +
   `GenContextResidentBytes()`. Pinned by
   `TEST_CASE("cache slots sizing does not charge resident scratch twice")`
   (`test_qwen_moe_exp_loader`, 94 assertions / 10 cases).

The verdict logic now distinguishes capacity from regression: `PerfCause::kCapacity`,
`AttributeDegrade(model_ratio, probe_ratio, actual_slots, baseline_slots)`,
`expert_cache_slots` on the entry/result path, and a `CAPACITY (not a
regression)` WARN branch — pinned by `test_perf_baseline_logic`
(169 assertions / 19 cases), including a byte-exact "the tracked baseline file
is what the harness writes" round-trip.

### Perf attribution and the open residual

Forced-slot sweep on the real weights (one run each, card idle between):
4 962 → 41.40 t/s (hit 0.826), 5 350 → 43.00 (0.862), 5 750 → 44.15 (0.887),
6 000 → OOM, 7 000 → OOM, 9 000 → indexer state allocation failure. The
2026-10-14 reference of 44.85 t/s needs ≈5 960 slots, which this card state
cannot hold, so the residual is **capacity**.

nsys over 64 decode steps: step window 25.23 ms, kernels 17.78 ms, H2D
5.58 ms/token (302 MB, 17 267 copies) — kernels + copies are 23.36 ms of the
25.23 ms window, i.e. essentially **no overlap**. Every H2D copy rides the
compute stream; the driver's dedicated copy stream carries 0.2 MB. Cause: the
family stages all ten experts' residency *before* any FFN compute, so there is
no window to overlap. **Closed on 2026-11-04**: staging now rides the copy
engine with per-expert `ev_uploads` and an `ev_front` slot-reuse fence, and the
routed TC chain runs in ascending chunks that wait only on their own uploads,
so the next chunk's H2D overlaps this chunk's TC compute (depth follows the
miss count; bit-exact, `logits_hash` unchanged). Measured −1.55% on `perf` at
identical slots/hit rate — the copies it hides were largely absorbed by the
capacity-bound loop. The section that tracked this item left
`docs/OPEN_TASKS.md` when it closed; its text is §6 of the lifecycle trail.

Ruled out by measurement: `LSX_MOE_TC_HOIST` (43.0 vs 42.9), a pageable
zero-copy regression (none), environment (probe nominal 1 524/1 531 GB/s), and
a `WaitEventChecked` spin-loop change (43.0 — no gain, reverted).

### Architecture as implemented

- 48 layers = 12 × (3 × GatedDeltaNet → MoE, then 1 × QSA attention → MoE);
  full-attention layers at indices 3, 7, …, 47.
- GatedDeltaNet: 16 key / 48 value heads × 128 dims, depthwise conv kernel 4.
- QSA attention: 24 Q / 2 KV heads × 256 dims, partial RoPE on 64 dims (θ 1e7),
  sigmoid output gate, plus a 4-head × 128-dim indexer over 4-token blocks with
  a 2 048-token budget and top-512 block selection.
- Hyper-connections: four residual streams recombined by learned gates through a
  rank-320 low-rank projection, before attention and before the MoE.
- MoE: 512 routed experts top-10 at intermediate 640, one shared expert at 640.
- PLE: layer 2, n-gram size 3, 8 heads per gram → 16 heads × 160 dims, with a
  depthwise conv (kernel 4, dilation 3) and its own norms.
- Geometry: hidden 2 560, vocab 248 320, `rms_norm_eps` 1e-6, context 262 144.
- Stripped and counted: 333 `model.visual.*` tensors, one MTP layer.
