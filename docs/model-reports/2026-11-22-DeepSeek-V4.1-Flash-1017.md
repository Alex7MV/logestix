## Part 1 — publish-ready post

### What was converted, and where it was run

**DeepSeek-V4.1-Flash-1017** is the 2026-10-17 update of DeepSeek-V4.1-Flash: a
552B-parameter mixture-of-experts language model with a 1M-token context window,
built on the CED (causal encoder-decoder) sparse-attention design — compressed
sparse attention over shared per-source-layer KV, a hierarchical sparse indexer,
hyper-connection residual mixing, conditional n-gram memory ("engram"), and a
speculative draft head.

The update turned out to be a **weight release, not an architecture release**,
and that is the single most useful fact for anyone converting it. Comparing the
two published trees field by field:

| evidence | result |
|---|---|
| `config.json`, `inference/config.json`, `tokenizer.json`, `tokenizer_config.json`, `model.safetensors.index.json` | byte-identical |
| tensor names / shapes / dtypes in the shard headers | identical |
| shard payload bytes | different (re-trained) |
| `inference/model.py` | 3 deltas, all in the *runtime* path |
| vendor encoder (`encoding/encoding.py`) | tool-result merge and turn-boundary refinements |
| `chat_template.jinja` | new in this tree |

So the converted artifact has the same geometry, the same tensor layout and the
same decoding semantics as the parent, and the work is a *sibling ingestion*:
one converter, one loader and one kernel set serve both checkpoints, and each
tree resolves to its own model identity.

Hardware: one RTX 5090 (32 GiB, SM 12.0), 768 GB host RAM, 160 hardware
threads, Ubuntu 26.04, CUDA 13.5 toolkit on a 13.4 driver, host compiler
AOCC clang 17 in Release (`-march=znver4`, LTO).

Artifact: 294 GB under `<model>/logestix/` — 1246 pinned dense tensors plus
15360 routed experts (384 per layer × 40), 4-bit weights with FP8-sourced dense
projections carried at source precision, norms and biases never quantized.
Routed experts stay on host as memory-mapped views behind a bounded LRU with a
device slot cache (954 slots × 19.9 MiB ≈ 19 GiB), which is what makes a 552B
model answer inside 32 GiB of VRAM at all.

### What the checkpoint forced into the engine

The architecture is the parent's, so the semantics below are inherited — but
they are the ones that silently produce "answers, but not the model's answers",
so they are restated per checkpoint:

1. **Layer-specific attention modes.** `compress_ratios` is
   `[0,0,2×18,1×20]`: layers 0–1 are pure sliding-window (window 128), layers
   2–19 pool every 2 tokens into the compressed cache, layers 20–39 project
   without pooling. A uniform pattern assumption decodes garbage.
2. **Shared caches with designated producers.** Main compressed KV comes from
   layers {2, 8, 14, 20}; the sparse indexer from {2, 8, 14, 20, 24, 28, 32, 36};
   the hierarchical candidate block mask (block 8, up to 2048 blocks) from layer
   20. Consumers read what an earlier layer wrote in the same in-order walk.
3. **Two RoPE regimes.** Compressed layers use θ = 160000 with YaRN
   (factor 16, original length 65536, β_fast 32 / β_slow 1); pure sliding-window
   layers use θ = 10000 and no YaRN. Attention applies the inverse rotation to
   its output.
4. **`rms_eps = 1e-20`**, not 1e-6. This one silently changes every normalized
   vector.
5. **Router**: `sqrtsoftplus` scores, a selection-only bias (it never scales),
   top-6 of 384, renormalized over the selected set, then × 1.5. One shared
   expert on every token.
6. **SwiGLU clamps**: up clamped to ±10, gate to (−∞, 10].
7. **Hyper-connections**: 4 residual copies mixed by a computed 24-row matrix
   (pre/post/combine) normalized with 20 Sinkhorn iterations.
8. **Engram and the speculative draft head are not applied.** Engram (layers 1
   and 14) is ~98 GiB per table and was cut at conversion with a counted record;
   the 3-layer DSpark draft head is stored-not-applied, per policy. The vision
   tower and aligner are cut and counted (text backbone only).
9. **The 1017 reference act-quants the attention output** before the grouped
   output projection (`model.py:785` and `:1070`). That is a runtime activation
   rounding choice, not a weight or state change: it does not affect what the
   checkpoint *is*, and this engine feeds the output projection in BF16. It is
   recorded here because it is the one place where the two checkpoints'
   reference code differs in numerics, and a reader comparing logits against the
   vendor stack should know.

Reference used: the checkpoint's own `inference/` stack (`model.py`, `kernel.py`,
`convert.py`) as the semantic source of truth, cross-checked against the parent's
already-verified engine implementation.

### Artifact-level traps found in the checkpoint

1. **The card name is the only thing that distinguishes the two trees.** Both
   convert to the same artifact format and both carry an index `model` field
   that path auto-detection folds into a model identity. A converter that stamps
   a fixed name makes the sibling tree resolve to the parent's model — the
   weights load, nothing errors, and two models' outputs are compared against
   each other's goldens. This engine now derives the field from the input
   tree's directory name and **rejects at load** a converted tree whose card
   name folds to a different model identity. *Suggestion to the authors:* state
   the checkpoint's own card name in `config.json` (the `architectures` field is
   shared by both releases), so downstream tooling has something to key on
   besides a directory name.
2. **The two `encoding.py` revisions disagree on turn boundaries.** The update
   treats a user message holding only tool results as *not* starting a new turn,
   and validates content blocks before merging. A bridge that ports one revision
   and serves the other renders different conversation shapes. This engine
   pins the text-only chat-mode rendering against the parent's committed goldens.
3. **`tokenizer_config.json` carries no chat template.** The chat template ships
   as a separate `chat_template.jinja`, and the update adds a
   "Reasoning Effort: 75" system line in thinking mode that the vendor encoder
   does not emit. Capture a golden with one and evaluate with the other and you
   get a prompt mismatch that looks like a model divergence. *Suggestion:* ship
   the template inside `tokenizer_config.json`, as most HF releases do.
4. **`tilelang` pin moved 0.1.8 → 0.1.12** in `inference/requirements.txt`
   between the two trees, with the two `act_quant` call sites above. Nothing in
   the published text documents either change.

### Measured numbers (AOCC Release tree, one GPU, serial)

| gate | result |
|---|---|
| SelfCheck ("The capital of France is") | **PASS** — `Paris`, 3 bit-exact cycles, `logits_hash 94974df500455a90`, top-1 token 11111 |
| Cooperative cancel | **PASS** — streams the produced tokens in order and stops on abort |
| Tool round-trip (native DSML) | **PASS** — `get_weather {"city":"Paris"}`, 40 assertions |
| FSI parity | **3/3** |
| CODE parity | **2/3** — CODE-03 reported red by an extractor artifact (below) |
| DET determinism | **3/3**, `deterministic=true` across three runs per case |
| Perf, canonical 2048-token protocol | **16.27 t/s**, TTFT **488 ms**, **231 W** average / 249 W peak |

The CODE-03 red deserves plain language: the probe asks for a regular expression
matching exactly four uppercase hex characters with word boundaries, and the
model answers `\b[A-F0-9]{4}\b` against the template's `\b[0-9A-F]{4}\b`. Those
are the same PCRE expression — member order inside a character class is
meaningless — but the gate's extractor locates the answer by a literal anchor
and therefore reports an empty extraction. It is recorded as a red rather than
declared green, because the honest fix is to make the extractor canonical and
re-measure every model's CODE gate, not to call this one a pass.

Throughput is the parent's shape (16.43 t/s on the parent's `perf` row), which is
what identical geometry with re-trained weights should produce: the decode is
weight-streaming bound, so a re-trained 4-bit body moves the same bytes.

### What was not measured, and why

- **Source-faithful parity.** The vendor reference is a 552B FP8/FP4 tensor-
  parallel stack targeting 2×80 GB; it cannot execute on one 32 GB card. The
  FSI/CODE/DET goldens therefore carry the prompt set's Expected Template as the
  expected answer — they pin the **converted path** (framing, tokenizer,
  sampling, 4-bit numerics against a fixed target) and say nothing about source
  parity. This is a recorded deviation in each golden's `source` field.
- **Vision, engram and speculative decoding.** Cut or stored-not-applied by
  design; no multimodal probe was run.
- **Context beyond the probe.** The KV design targets 1M tokens (890 bytes/token
  in the reference); the gates here run short prompts. Long-context behaviour is
  untested on this card.
- **Label sweeps.** Verification was scoped to this model's targets plus the
  fast guard suite, per the ingestion protocol; no `inference`/`convert` label
  sweep was run (they are infrastructure instruments, hours of serialised GPU).
