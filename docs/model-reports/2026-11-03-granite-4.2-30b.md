## Publish-ready post

### Notes from an independent NVFP4 port of granite-4.2-30B

We run IBM Granite 4.2 30B in our own C++/CUDA inference engine (no PyTorch at
runtime). The 54.5 GiB BF16 release converts in place to a 15.3 GiB NVFP4 tree
that fits entirely in the 32 GB of a single RTX 5090 and loads in about 1.2 s.

The architecture is a plain dense decoder: 64 layers, 4096 hidden, 32 query /
8 KV heads of 128 dims, a 32 768-wide SwiGLU MLP, full-dimension RoPE with
θ = 5·10⁷, and the Granite fixed attention scale `1/128`
(`attention_multiplier`). There is no MoE, no QK-norm and no bias.

#### What worked well

- **Determinism is solid.** The control prompt answers "Paris" and three
  independent runs produce byte-identical full-vocabulary logits
  (`logits_hash = c165e80fde6401cf`). The parity goldens (FSI, CODE, DET) all
  match the source-captured answers, and DET reproduces its token stream on
  three consecutive runs.
- **Native tool calling works.** With the checkpoint's own ChatML/tool framing
  the model emits `<tool_call><function=get_weather><parameter=city>Paris…`;
  the engine parses it back to `get_weather {"city":"Paris"}`.
- **One shot per token.** A 16 GB tree on a 32 GB card leaves ample room for
  the KV cache; at 2 048 tokens the model decodes at ~76.8 tokens/s.

#### The one thing that needed care

The 4-bit NVFP4 tensor-core path quantizes **activations** to E2M1 with E4M3
block scales. Granite's long tool/template prompt drives a few activations past
that range, and the tensor-core prefill then clamps: the generated text
collapses into repeated fragments (`_with_n_comprehension…`, or `## Example 2`
on the engine's own framing). Switching the family to the strict FP16-activation
path fixes it completely — the converted model then reproduces the source
model's tool call token-for-token. We verified this against the actual BF16
checkpoint running on CPU: given the exact reference prompt, the source emits

```
\n<tool_call>\n<function=get_weather>\n<parameter=city>\nParis\n</parameter>\n</function>\n</tool_call>\n
```

and the NVFP4 engine under the strict path emits the same ids. The cost is the
tensor-core speed-up on this family (perf row 77.86 → 76.79 t/s); correctness
wins.

## Internal evidence

### Conversion

`lsxforge --granite --input <src> --output <src>` (in place) emits
`<src>/logestix/model.index.json` (`"format": "logestix-granite"`,
`total_pinned_tensors = 387`) and `logestix/pinned/*.arrow`. Geometry is checked
against the frozen passport before conversion: 64 layers / 4096 H / 32 Q · 8 KV
/ 128 HD / 32 768 I / vocab 100 352, `attention_multiplier = 0.0078125`,
`rope_theta = 5e7`.

### Gates (real weights, `linux-release-znver4-aocc`)

- `test_granite_dense_selfcheck` — PASS. `top1_tok=12366 text='Paris'`,
  `logits_hash=c165e80fde6401cf` identical over 3 cycles; native tool
  round-trip `get_weather {"city":"Paris"}`.
- `test_granite_dense_fsi_selfcheck` — PASS 3/3.
- `test_granite_dense_code_selfcheck` — PASS 3/3.
- `test_granite_dense_det_selfcheck` — PASS 3/3, `runs=3 deterministic=true`
  for each prompt.
- `test_granite_dense_model`, `_loader`, `_kernels`, `_convert`,
  `test_granite_tool_framing`, `test_model_independence_guard` — PASS.

The parity tests pin `FastMathMode::kOff`; the tool round-trip previously used
the default auto policy and was the RED gate that exposed the defect below.

### Defect found and fixed (TDD)

1. RED: `test_granite_dense_selfcheck` tool round-trip failed on real weights —
   generated an "example explanation" then malformed XML; no tool call parsed.
2. Confirmed with an external oracle: the source BF16 checkpoint (CPU) emits
   the correct `<tool_call>` for the exact reference ids, while the converted
   model on the auto/TC path emitted `_with_n_comprehension…`.
3. Root cause: the NVFP4 tensor-core path's E2M1×E4M3 activation range is
   exceeded by this prompt.
4. Fix: pin `FastMathMode::kOff` in `Granite42_30BModel::Infer` (the
   `granite-switch` sibling already does this). GREEN: the tool round-trip
   passes and reproduces the source ids.

A secondary observation (non-blocking): the engine renderer emits the tool
`parameters` JSON compactly and appends a trailing newline after
`<think></think>`, where HuggingFace's `chat_template.jinja` uses Python
`tojson` spacing and no trailing newline. The strict path reproduces the source
tool call under either framing, so this was left unchanged.
